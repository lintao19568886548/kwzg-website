# 官网线索工作台设计与数据定义

本文记录 Stage 2.2 官网独立线索后台的数据口径、优先级、未读规则和数据库兼容策略。后台只处理 `yizuw.org` 预约线索，与 `yizuw.cn` 生产系统隔离。

## 指标口径

所有日界线使用 `Asia/Shanghai`，由服务端生成参数化查询边界。六项指标由一次线索聚合查询、一次本月成交审计查询和当前管理员未读查询构成，不在前端拼数，也不以加载失败替代为 0。

| 指标 | 定义 |
| --- | --- |
| 今日新增 | `created_at >= 当天00:00` 且 `< 次日00:00` |
| 待跟进 | `status = PENDING` |
| 今日应跟进 | `next_follow_up_at` 位于当天范围，且状态非 `WON/INVALID/CLOSED` |
| 已逾期 | `next_follow_up_at < 当前时刻`，且状态非 `WON/INVALID/CLOSED` |
| 已预约演示 | `status = DEMO_SCHEDULED` |
| 本月已成交 | 本月 `lead_audit` 中 `STATUS_CHANGED` 且 `after_value.status = WON` |

任务区优先级为：逾期、最早提交的新线索、今日跟进、普通线索。每区由服务端限制返回数量，避免一次加载全部记录。

## 未读计算

`admin_lead_read_state` 使用 `(admin_user_id, lead_id)` 联合唯一键，保存 `read_at` 与 `last_seen_lead_updated_at`。未存在读取记录，或 `leads.updated_at` 晚于最后查看版本时判定未读。

打开详情只在首次查看时追加一次 `LEAD_VIEWED` 审计，同时更新当前管理员读取状态。当前管理员完成状态、跟进或演示事务后，同一事务同步其已读版本；其他管理员仍按各自读取状态计算。

读取状态属于界面状态，不写入业务审计。

## 状态、跟进与演示

状态流转继续复用 `shared/lead-statuses.js` 和 Stage 2.1 工作流规则。跟进写入 `lead_follow_ups`，状态变更与审计在事务内完成。演示预约使用独立字段 `demo_scheduled_at`、`demo_method`、`demo_note`，禁止把时间塞进普通备注后解析。

时间线合并只追加的审计和人工跟进，按时间倒序分页；跟进已有对应审计时避免重复渲染同一事件。

## 数据库迁移

`202608250002_add_admin_workbench.js` 为 Stage 2.1 数据库增量增加：

- 演示时间、方式和备注字段；
- 演示时间以及状态与下次跟进组合索引；
- 管理员维度的线索读取状态表、联合唯一键和外键索引。

迁移不删除既有字段、线索、跟进或审计，字段允许为空，兼容空数据库和已经应用 Stage 2.1 的数据库。迁移由 Knex 正式迁移命令执行，不手工修改数据库。

## 安全和性能边界

- 所有工作台、读取状态、详情、跟进、演示和账户 API 必须经过服务端管理员鉴权。
- 完整手机号只在已认证详情和明确授权导出中返回，不写入日志或 localStorage。
- 聚合查询使用连接池、参数绑定和有限任务列表，不执行 N+1 查询。
- 常用索引覆盖状态、创建时间、下次跟进、演示时间、负责人、审计/跟进的线索时间组合及读取状态联合键。
- 数据库不可用返回 503，界面显示失败态，不产生假 0 或假成功。
