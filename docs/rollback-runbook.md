# 生产回滚手册

## 触发条件

出现持续健康检查失败、公开路由大面积 5xx、预约错误成功、后台越权、数据库迁移异常、关键静态资源缺失或无法快速缓解的安全问题时，停止继续发布并进入回滚。

## 回滚前判断

1. 冻结新的部署和迁移操作，记录当前提交、镜像、迁移批次与故障时间。
2. 确认上一版本的提交和不可变镜像仍可取得。
3. 先判断数据库迁移是否向后兼容。禁止在不理解数据影响时直接执行 `db:rollback`。
4. 当前迁移仅允许由单独的 `migrate` 服务执行；应用副本不执行迁移。
5. 如涉及破坏性或数据转换迁移，优先修复前滚；确需恢复时恢复到新的数据库实例，验证后再切换，禁止覆盖唯一生产库。

## 应用回滚

1. 保留故障版本日志和必要证据，但不得复制密码、Token、完整手机号或请求正文。
2. 将 `KWZG_IMAGE_TAG` 改为上一已验收镜像标签。
3. 如果数据库结构与旧应用兼容，跳过迁移服务或确认其不会执行新变更，再替换应用容器。
4. 等待 `/api/health` 通过后再恢复代理流量。

## 数据库恢复场景

1. 按《数据库备份与恢复》确认备份时间、校验值和恢复目标。
2. 创建全新的隔离数据库或卷，导入备份并检查字符集、迁移版本、预约记录和审计记录。
3. 所有管理员 Session 视为需要失效；清空恢复库中的 `admin_sessions` 后重新登录。
4. 使用只读检查确认记录完整，再在维护窗口切换应用连接。
5. 禁止对不确定目标执行 DROP，禁止覆盖原库作为首次恢复尝试。

## 回滚后验收

1. 检查 `/api/health`、13 个公开路由、案例 404、静态资源和安全响应头。
2. 使用专门测试线索检查预约 201、后台可见、幂等和数据库审计记录。
3. 检查后台登录、详情、退出撤销、CSV 权限与 no-store。
4. 检查 `/call`、企业微信二维码和当前 noindex 状态。
5. 记录故障根因、回滚版本、数据库状态、数据影响与后续修复负责人。
